# Baby Daybook Garmin Watch Experience Specification

Status: Proposed

Implemented Through: `67422607b63bd0a42131f0983da12c5fa77b4b0d`

Purpose: Define the next watch interaction, event-audit, bottle, diaper, and sleep behavior together with screenshot-based acceptance evidence.

## Normative Language

The key words `MUST`, `MUST NOT`, `REQUIRED`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `MAY`, and `OPTIONAL` are to be interpreted as described in RFC 2119.

`Implementation-defined` means the behavior is part of the implementation contract, but this specification does not prescribe one universal policy. Implementations MUST document the selected behavior.

## 1. Problem Statement

The watch currently records bottle, wet-diaper, and dirty-diaper events and synchronizes them through the relay. The bottle amount picker is visibly misaligned, bottle records do not let the caregiver distinguish Mother’s milk from Formula, one action cannot record a combined wet-and-dirty diaper, and sleep cannot be started or stopped from the watch. Acknowledged queue entries are removed, so the watch also lacks an audit trail that can answer whether an event was actually submitted.

## 2. Goals and Non-Goals

### 2.1 Goals

- Every supported flow MUST be usable with both the Fenix 7 button model and its touch screen where Garmin supplies equivalent native interaction.
- The bottle amount selector MUST be visually centered and legible.
- A caregiver MUST be able to select Mother’s milk or Formula for a bottle, and the watch MUST remember the last confirmed choice.
- A caregiver MUST be able to record a combined wet-and-dirty diaper in one action.
- A caregiver MUST be able to start or stop the baby’s active sleep timer.
- The watch MUST expose a durable, watch-only event log that distinguishes pending, acknowledged, and failed submissions.
- Each user-visible state and transition MUST have screenshot-based simulator acceptance evidence produced through Garmin Pilot.

### 2.2 Non-Goals

- The watch event log is not a replacement for the complete Baby Daybook timeline.
- The watch does not edit arbitrary phone-originated activities.
- Sleep pause/resume, sleep quality, and retrospective sleep-time editing are not part of this iteration.
- Bottle categories other than Mother’s milk and Formula are not part of this iteration.

## 3. System Boundary and Terminology

- **Watch app**: the Connect IQ application and its persistent `Application.Storage` state.
- **Relay**: the authenticated HTTPS service that accepts watch operations and writes Baby Daybook records.
- **Watch event**: an operation whose stable identifier was generated by the watch app.
- **Submission ledger**: the ordered watch-only audit history shown by Event log.
- **Pending**: durable on the watch but not yet acknowledged by the relay.
- **Synced**: acknowledged by the relay as created or already present under the same stable identifier.
- **Failed**: not currently acknowledged and blocked by an operator-visible permanent or authentication error. Retryable transport failures remain Pending with an error annotation.
- **Milk kind**: exactly one of `mothers_milk` or `formula`.
- **Active sleep**: the newest non-deleted `sleeping` activity whose `inProgress` value is native true.

## 4. Navigation and Home Menu

The home menu MUST present these actions in this order:

1. Bottle
2. Wet diaper
3. Dirty diaper
4. Wet + dirty diaper
5. Sleep (or Stop sleep while a sleep is active)
6. Sync
7. Event log

Setup-required UI MAY precede these actions when credentials are absent.

The Event log entry MUST remain directly below Sync. Menu labels MUST fit the supported Fenix 7, Fenix 7S, and Fenix 7X profiles without clipping that changes their meaning.

## 5. Bottle Flow

### 5.1 Milk Kind

Opening Bottle MUST present the remembered milk kind. On a fresh or migrated installation with no valid remembered value, Mother’s milk MUST be selected.

The caregiver MUST be able to change the kind between Mother’s milk and Formula before confirming. Cancelling the flow MUST NOT change the remembered kind. Confirming a bottle MUST atomically persist the selected kind as the new default and enqueue it with the bottle event.

The relay MUST resolve `mothers_milk` and `formula` to the baby’s corresponding non-deleted bottle groups. It MUST NOT silently substitute a different group. If the requested group cannot be resolved, the event MUST remain visible as Failed or Pending with an actionable error and MUST NOT be acknowledged.

### 5.2 Volume Picker

The picker MUST initialize to the last confirmed bottle volume, falling back to the configured default. Cancelling MUST NOT change the remembered volume. Confirming MUST persist the selected volume.

The selected volume text and unit MUST be horizontally centered on the display’s center axis. Its visible bounding box MUST remain inside the safe round-display region and MUST NOT overlap the title, arrows, confirmation affordance, or bezel on Fenix 7, Fenix 7S, or Fenix 7X.

The picker MUST retain the configured minimum, maximum, and 0.5 US-fluid-ounce step behavior. The relay MUST continue storing volume in milliliters.

## 6. Diaper Flow

The three diaper actions MUST enqueue these exact flag combinations:

| Action | `pee` | `poo` |
|---|---:|---:|
| Wet diaper | true | false |
| Dirty diaper | false | true |
| Wet + dirty diaper | true | true |

Each action MUST use one stable event identifier and MUST show a confirmation label that unambiguously identifies the selected combination. A combined event MUST appear as one ledger row and one Baby Daybook activity, not two independent events.

## 7. Sleep Flow

The watch MUST implement the same toggle semantics as the Homey integration:

1. Before starting, the relay MUST query for an Active sleep.
2. If none exists, selecting Sleep MUST create one `sleeping` activity with `inProgress` true and `startMillis` set to the operation time.
3. If an Active sleep exists, the home action MUST render as Stop sleep. Selecting it MUST update that same activity with `endMillis` equal to the operation time, `duration = max(0, endMillis - startMillis)`, and `inProgress` false.
4. Stop MUST target an Active sleep even when it was started by the phone or Homey.
5. Repeating a start or stop operation with the same watch operation identifier MUST be idempotent.

The watch MUST show whether sleep is active after a successful pull or toggle. While offline, a requested transition MUST be durable and visible in the submission ledger. Conflicting state discovered during synchronization MUST resolve without creating overlapping watch-started sleep records; the watch MUST show the resulting failure or resolved state rather than silently discarding the operation.

## 8. Watch Event Log

### 8.1 Scope and Ordering

Event log MUST show watch-originated submissions only. Phone-, web-, SDK-, and Homey-originated activities MUST NOT appear unless they were originally created by a watch operation with the same stable identifier.

Rows MUST be ordered newest first. Every row MUST expose at least:

- event kind;
- local event time;
- Pending, Synced, or Failed status;
- bottle volume and milk kind when applicable;
- wet/dirty flags when applicable;
- start/stop meaning for sleep operations.

### 8.2 Durability and Reconciliation

Acknowledging an event MUST remove it from the upload queue but MUST NOT remove it from the submission ledger. Retry and app restart MUST NOT duplicate a ledger row.

The local log MUST retain the newest 10 watch-origin operations. Acknowledgement updates MUST preserve those rows until newer operations evict them.

When an eleventh operation is submitted, the implementation MUST evict exactly the oldest log row and retain the newest 10.

## 9. Failure and Recovery

- Enqueueing MUST precede network I/O for bottle, diaper, and sleep operations.
- Authentication failure MUST retain the operation and show setup/authentication guidance.
- Retryable network failure MUST retain the operation as Pending.
- Permanent validation failure MUST retain an audit row as Failed with a safe user-visible reason.
- Secrets, refresh tokens, baby identifiers, and raw server payloads MUST NOT appear in the event log or screenshots.
- A successful retry MUST transition the existing row to Synced rather than append a second row.

## 10. Screenshot Acceptance Contract

Garmin Pilot MUST produce screenshot artifacts for the exact profile under test. Visual tests MUST use stable simulator state and MUST retain a baseline plus post-action image.

Required screenshot scenarios:

1. Home menu showing Wet + dirty diaper, Sleep/Stop sleep, Sync, and Event log in the specified order.
2. Bottle flow with Mother’s milk selected.
3. Bottle flow with Formula selected.
4. Centered bottle volume at minimum, default/remembered, and maximum values on Fenix 7, 7S, and 7X.
5. Wet + dirty confirmation.
6. Sleep inactive and active home states.
7. Sleep-start confirmation and sleep-stop confirmation.
8. Event log containing representative Pending, Synced, and Failed rows.
9. Event-log bottle and combined-diaper detail.
10. Offline-to-synced status transition for the same stable row.

Screenshots MUST be reviewed for clipping, overlap, centering, round-screen safe-area violations, ambiguous selection, and incorrect status—not merely for pixel-file existence.

## 11. Test and Validation Matrix

### Navigation and Rendering

- Unit: menu construction produces the required actions and order for provisioned and setup-required states.
- Simulator screenshot: Fenix 7, 7S, and 7X render every home entry without ambiguous clipping.

### Bottle

- Unit: fresh default, remembered selection, confirm persistence, and cancel non-persistence are covered for both milk kinds and volume.
- Unit: relay validation accepts only the two milk-kind identifiers and resolves the matching non-deleted group without fallback.
- Simulator input: buttons and touch can select each kind and confirm a bottle.
- Simulator screenshots: minimum, remembered/default, and maximum volume are centered on all three target sizes.
- Integration: the acknowledged Baby Daybook record contains the selected group and converted milliliter volume.

### Diaper

- Unit: all three flag combinations match the table in Section 6.
- Simulator input and screenshot: Wet + dirty creates one confirmation and one ledger row.
- Integration: the Baby Daybook record has both native flags true and no duplicate companion record.

### Sleep

- Unit: no active sleep starts a timer; an active sleep stops the same identifier; duration clamps at zero; repeated operation identifiers are idempotent.
- Integration: timers started through Homey or the phone can be stopped through the watch relay.
- Simulator input and screenshots: inactive → active → inactive states and confirmations are visible.
- Failure integration: offline/conflicting transitions remain auditable and do not create overlapping records.

### Event Log

- Unit: newest-first ordering, stable row identity, status transitions, restart recovery, and separation from the upload queue.
- Integration: relay reconciliation returns only watch-origin submissions and preserves audit evidence after upstream edits/deletions.
- Simulator screenshots: representative Pending, Synced, Failed, bottle, diaper, and sleep rows are legible.
- Capacity: after an eleventh submission, exactly the oldest row is evicted and the newest 10 remain reachable in newest-first order.

### Automation Harness

- Automated: Garmin Pilot builds and loads Garmin’s Input sample, drives Down and tap, observes a screenshot change after each, and detects new `CIQ_LOG.YML` entries.
- Diagnostic: synthesized swipe MAY be exercised explicitly, but MUST NOT gate acceptance because Garmin exposes no supported simulator input endpoint and synthesized drags are not consistently recognized.
- Automated: Toolcraft screenshot, press, tap, and optional swipe commands close their `monkeydo` sessions.

## 12. Conformance Criteria

An implementation conforms when:

- every `MUST` and `MUST NOT` requirement is satisfied;
- the complete unit and integration matrix passes;
- every required screenshot scenario exists and has been visually reviewed;
- Fenix 7, Fenix 7S, and Fenix 7X builds succeed;
- no tested flow adds a new simulator crash-log entry;
- watch submission history demonstrates no silent loss or truncation.

## 13. Open Questions

1. Historical migration: can all watch-origin records created before explicit provenance metadata be identified reliably from their stable identifier format, or must the log label pre-migration history as incomplete?
2. Upstream deletion display: should a watch-submitted event later deleted on another client remain labeled Synced with a deletion annotation, or receive a distinct Deleted status?
3. Sleep conflict UX: when an offline watch start races with a phone-started sleep, should the relay reject the watch operation as Failed or reconcile it to the phone activity and label it Synced with a conflict annotation?
